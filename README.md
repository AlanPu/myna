# Myna

AI 口语跟读播放器。把一个 YouTube 视频变成可以逐句慢速跟读的材料:音频按原速播放,字幕逐词高亮跟随人声,任意一句可以循环重复,还可以录下自己的一句让程序告诉你**差在哪里**。

不依赖 TTS。慢速版本用 `atempo` 渲染,保留原始音色和音高——跟读要练的是**你的发音**,不是模仿一个合成声音。

## 快速开始

```bash
./play.sh                 # 打开 http://127.0.0.1:8777/index.html
```

页面上方的「换视频」可以直接粘贴新的 YouTube 网址重建。留空则继续用当前视频,时长填 `0` 表示截取完整音频。

手动重建:

```bash
export https_proxy=http://127.0.0.1:7890        # 需要代理时
.venv/bin/python rebuild.py "<url>" 0 180 "标题"    # url / 起点 / 时长(0=完整) / 标题
```

`rebuild.py` 跑完会自动执行验证,任何一项不过就返回非零并拒绝交付。

## 跟读打分

页面上点 🎤(快捷键 `V`):**先播一遍原声,然后才打开麦克风**,你跟着读,再点一次结束。程序给出 0–100 分和逐词标记。

流程是「先听后说」而不是「边播边录」,因为麦克风只在原声结束后才开,不会把自己的声音和原声录在一起。

**不识别你读成了什么。** 没有语音识别,没有模型。原声和录音走**同一条**分析链路:都先降采样到 16k,再各自提取音节核峰,最后用 DTW 对齐两条峰序列。判断的是「我的节奏和原声差多少」,不是「我读对了吗」。

由此带来的边界,写在下面「已知的取舍」里。

分数由三项加权而成:

| 项 | 权重 | 含义 |
|---|---|---|
| 节奏 | 0.55 | 每个音节落点与原声的偏差(已扣除测量噪声底) |
| 完整度 | 0.30 | 有多少个词在原声给它的位置里被读了出来 |
| 音节数 | 0.15 | 你发出的音节数与原声的比值 |

界面上另外单独给出语速(快/慢百分之多少)和起音时间,这两项**不计入分数**。

## 流程

```
rebuild.py
  1 下载音频(按视频 ID 缓存)
  2 抓字幕 → 重新分组为句子          sentences.py
  3 切片
  4 渲染 4 档变速(atempo,保音高)
  5 实测每句语音边界 + 逐词标记      onsets.py wordmarks.py
  6 写清单
  7 跑六项验证                      check.py
```

`serve.py` 提供静态文件,以及 `POST /api/build`(浏览器触发生成)、
`POST /api/score`(上传一次跟读并评分)和 `GET /api/score?index=N`(查询参考统计)。

## 这个项目最难的部分

高亮必须**跟着人声走**,而不是跟着字幕时间戳走。这两件事不一样,而且差得很远。

**字幕窗口是滚动的,会重叠。** 自动字幕按"显示时长"切段,一段字幕会在下一段开始后仍然挂着。18 分钟的片段里 229 对相邻句子中 120 对窗口重叠,平均提前约 2 秒开始。所以拿字幕窗口当句子边界,循环跟读时会把下一句的开头混进每一次重复——第一句实际只有 4.44 秒语音,窗口却到 6.40 秒。

**高亮的粒度问题在词,不在句。** 自动字幕的时间戳只到句,没有词级信息。`wordmarks.py` 用 RMS 包络 + 音节核检测找出 5377 个候选峰,再按时间把峰切分给每个词,每段取其中能量最高的那个。当前构建 3048 个词全部落位。

**验证必须来自波形,不能来自数据自洽。** 这一条花了最久。早期写的检查都是把播放器和它自己的数据对比,结果连续三次报告"通过"而实际高亮明显滞后。这些检查**在结构上就无法发现滞后**。现在高亮侧只有两项检查是有信息量的:

| 检查 | 判据 |
|---|---|
| `verify_switch.py` | 每句的最后一个词在被替换前必须点亮 |
| `verify_visual.py` | 每个标记之后 250ms 内必须有真实语音 |

打分的验证换了另一条路子:**往原声里注入缺陷,看分数掉不掉。** 这是波形层面的判据,不是自洽。

| 用例 | 注入 | 当前均值 |
|---|---|---|
| good | 原声重读 | 96.2 |
| lead | 前面加 400ms 采集延迟 | 95.7 |
| late | 第二个音节前犹豫 90ms | 85.5 |
| noisy | 6dB 信噪比 | 72.0 |
| gap | 句中挖掉 1.2s | 70.7 |
| slow | 拉慢 1.30 倍 | 43.6 |
| thin | 压到 0.75 倍(音节数掉到 0.55–0.9) | 34.7 |
| fast | 加快 0.80 倍 | 40.5 |

`thin` 是这一节里唯一断言「能算出分」而不是「分够高」的用例。它对应下面这个 bug:DTW 的带宽是 `0.35 × 序列长度`,比两个序列的**长度差**还窄,所以当读得比原声少几个音节时,根本不存在一条从起点走到终点的路径,函数返回无穷大,句子只能回答「无法对齐」。

`verify_e2e_score.py` 另开一个真浏览器:用 Chromium 的假麦克风(喂真实句子切片)走完 MediaRecorder → 上传 → 评分 → 逐词标记落到 DOM 的全过程。这一条抓到过四个只在浏览器里才暴露的问题:录音了错误的句子、录音被截断、`ensureRunning` 的 ReferenceError 被 catch 吞掉、以及评分结束后字幕滑到下一句。

**合成夹具不够的时候,要真人录一遍。** 上面那个带宽 bug 走完了完整的一轮六项检查,全部通过。真人录 7 次里有 1 次失败,才暴露出它——因为所有合成夹具和假麦克风产生的音节数都接近参考,永远碰不到触发条件。查这类问题用服务端的两个开关:`MYNA_KEEP_TAKES=1` 把每次上传的原始录音存到 `/tmp`,`MYNA_SCORE_LOG=1` 打印一行 `index / t0 / score / ref_pk / user_pk / onset / need / got / conf / note`。这两个数字网页端拿不到——浏览器不知道服务端看见了什么。

当前构建:230 句,18.4 分钟。231 次切换中 229 句词全亮;3026 个词标记里 93% 后面跟着真实语音,59% 是明显发声的帧。

## 已知的取舍

**句间真实重叠。** 229 对相邻句子里有 120 对在录音里本来就重叠,最多到 4.08 秒。重叠期间屏幕显示的是上一句,而新句的语音已经开始。这是录音的属性,消除它需要改动切分逻辑,收益不明确。

**7% 的词标记落在换气停顿里。** 逐帧核对过,是真的停顿,不是 bug。高亮应该比声音早一点点亮。

**长片段的检查阈值。** 3 分钟片段零容忍成立,18 分钟下 0.9% 的句子因上述重叠丢词。`verify_switch.py` 因此按 2% 判定并打印最差情况。

## 打分的已知边界

**同音节的不同音素无法区分。** `ship` 和 `sheep` 的音节峰位置几乎相同,这套方法给同样的分。要判「读成了什么」必须上语音识别——这是有意的取舍,不是待办。

**句中 400ms 的停顿测不出来。** 挖掉 400ms 几乎不改变分数(那个词的起始音节还在),挖掉 1.2s 才会掉 5–29 分并出现「未读出」。这是对齐算法的分辨率极限,不是 bug。

**开头的沉默会被吸收,这有代价。** `getUserMedia` 打开麦克风要几百毫秒,没人会在录音的第一帧就开口,所以评分会自动在 0.6s 内寻找最合适的整体偏移(用同一个 DTW 试各个偏移,取最省的一个)。副作用:**真实的前置迟疑也在这 0.6s 内,同样被吸收**。超出 0.6s 的迟起才会如实计入并显示在「起音」上。换来的好处是 400ms 的采集延迟完全不扣分——这不可能靠前端上报来避免,浏览器自己也不知道这个数。

**噪声音效不扣分,但也不加分。** 6dB 信噪比下分数 72.0,比 good 低约 24。判据是「不能因为房间吵就惩罚学习者」,所以留了余量。这个数字以前是 76.8,看着更好,其实是**幸存者偏差**:旧带宽下有一半的噪声样本根本对不齐,被当成 `NaN` 丢掉了,76.8 只是「最好的那一半」的平均值。修好带宽后 8/8 都能评分,72.0 才是真实水平。

## 依赖

Python 3.12、`ffmpeg`、`yt-dlp`、`youtube-transcript-api`,浏览器检查需要 Playwright。慢速渲染不需要 `rubberband`。

`.venv/`、`audio2/`、`player/*.m4a` 和变速产物不入库——都由 `rebuild.py` 生成。
